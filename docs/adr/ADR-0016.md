# ADR-0016：欄寬貼齊內容，視窗尺寸由內容自然寬度推得

- 狀態：已決定
- 日期：2026-10-18

## 背景

ADR-0011 的前提是「表格是 9 欄橫向排列，內容本身的自然寬度本來就接近 1100」，所以把縮放下限夾在 0.85（對應視窗寬 935），窄於 935 之後超出的寬度由表格水平捲動消化。ADR-0008 則決定視窗開在 1100×760、最小 700×480，尺寸由 `config/portfolio.json` 自行持久化。

ADR-0015 把四個報酬欄改成金額／比率二選一之後，這兩個前提都鬆動：

- 欄位由 9 欄降為 7 欄（編輯模式 8 欄），內容自然寬度降到約 500；`table { width: 100% }` 把欄位平均拉開填滿視窗，使用者看到的是欄與欄之間的大片空白，而不是一個可以縮小的介面。
- 700×480 的下界與內容實際需要的 500×345 之間差了 200；而且 480/760 = 0.63 與縮放下限 0.85 不是同一個基準。
- 記住使用者拉過的尺寸，等於每次啟動都開在一個與內容無關的大小；實測啟動時視窗維持記住的 724×480，不會縮到內容邊界。

使用者要求：欄位減少後欄寬應該貼齊，介面才能縮得更小；寬度要縮到貼合欄位邊界；高度也要跟著縮；這個尺寸由資料決定。

## 決策

1. **欄寬貼齊內容**：`table { width: max-content }`。表格寬度由資料決定，不隨視窗拉開。這讓「內容需要多寬」從估計值變成可以量的實測值。
2. **視窗尺寸由內容推得**：
   - 寬度 = 內容在縮放下限（`MIN_SCALE = 0.85`）時的自然寬度。量測方式是把 `--scale` 固定在下限、`.app` 設成 `width: max-content`，讀 `getBoundingClientRect().width`，再加上目前的垂直捲軸寬度。取工具列、表格、總計列、狀態列的最大值。
   - 高度 = `minHeightFor(寬度) = round(寬度 × 760 / 1100)`，與 1100×760 的設計比例一致。
3. **啟動時、以及內容變動時，一律把視窗調到貼合內容**（`main.ts` 的 `applyWindowSize`）。`setSize` 的 `minWidth` / `minHeight` 就是這組尺寸，所以使用者只能把視窗拉大，不能拉到裁掉欄位。
4. **視窗尺寸不再持久化**：`config/portfolio.json` 移除 `windowWidth` / `windowHeight`，`resize` 監聽不再寫回尺寸。使用者手動拉大的視窗在下次啟動會回到貼合內容的大小。舊檔殘留這兩個欄位時直接忽略，不升 `schemaVersion`。
5. **垂直捲軸寬度即時量測，不預留**：拿 `board.offsetWidth - board.clientWidth`；沒有捲軸時為 0，視窗右緣因此完全貼齊內容。列數多到出現垂直捲軸時，這一塊會被算進寬度，視窗自動變寬，最右欄不會被捲軸擠掉。
6. **套用後再量一次收斂**：貼合會改變視窗高度，而高度決定垂直捲軸是否出現，也就決定寬度要不要多一個捲軸寬。`applyWindowSize` 套用並等尺寸穩定後重新量測，值有變就再套用一次（最多兩趟）。
7. **新增表單不列入量測**：表單列可換行（`flex-wrap`），不會造成水平溢出；列入量測會把寬度撐到約 700。量測時把表單寬度設為 0，不能改 `hidden`（會讓輸入框在輪詢重繪時失焦）。
8. 此決策**取代 ADR-0011 的「低於下限由表格水平捲動消化」與 700 下界**，並**取代 ADR-0008 的尺寸持久化決定與 ADR-0013 的尺寸還原、`resize` 寫回**。前述 ADR 本文依專案規則不修改。ADR-0013 的「`setSize` 收外框尺寸」換算仍然有效，貼合時照樣要換算成外框尺寸。

## 理由

- 欄寬貼齊之後，視窗尺寸可以直接由實測的內容寬度推得，不必再靠「1100 的 0.85 倍」這種與內容無關的換算。
- 水平捲動是前一個決策的產物，不是使用者要的功能：它把「視窗很窄」與「看得到資料」變成二選一。改成由內容決定尺寸之後，視窗的下限就是「所有欄位都還在」的那條線，捲動不會發生，也就不需要這個機制。
- 不記住視窗尺寸，是因為記住的尺寸與內容無關：持股只有 1 檔時記住 724×480，畫面右側與下方都是空白。既然尺寸可以從資料推得，交給偏好檔只是多一個會過期的來源（也正好符合 ADR-0008 想避開的「兩套來源」問題）。
- 高度按設計比例推導，是因為縮放下限已固定字級：字級不再跟著視窗縮放，視窗形狀就該沿用設計比例，而不是各自為政的 700×480。
- 不預留捲軸空間，是為了讓右緣完全貼齊內容：預留會在沒有捲軸時留下一條約 17px 的空白，那是使用者直接看得到的多餘空間。代價是捲軸出現時寬度需求會變，靠套用後再量一次收斂。
- 量測成本是每次 `refresh()` 兩次強制重排（輪詢每 5 秒一次）；`applyWindowSize` 每趟也會再量一次，但 `setSize` 只在尺寸真的變動時呼叫，不需要額外的監聽或快取。

## 後果

- **視窗尺寸不再是常數，也不再是偏好**：`src/main.ts` 的 `MIN_WIDTH = 700` / `MIN_HEIGHT = 480` 移除，改由 `measureMinSize()` 推得。實測（1 檔持股）：檢視模式 454×314（報價載入前）→ 469×324（報價載入後）；編輯模式 533×369；12 檔持股（列數超過視窗高度）時 511×354。
- 尺寸隨資料變動：股數、平均成本或報價欄位越寬，視窗越寬；新增或刪除持股、切換編輯模式與報酬顯示模式都會重新貼合。**列數多到出現垂直捲軸時，寬度再多一個捲軸寬**（實測約 17px），最右欄不會被擠掉。
- 使用者手動拉大的視窗不會被記住，下次啟動回到貼合內容的大小；拖拉仍可自由放大。
- `neutralino.config.json` 的 `minWidth` / `minHeight` 只在應用程式套用尺寸前有效，之後由 `setSize` 覆蓋；該檔不再需要與程式碼常數一致。
- 視窗寬度等於縮放下限對應的內容寬度，因此在 500–935 之間把視窗拉寬只會增加右側留白；縮放仍只在 935 以上才有變化（ADR-0011 的夾限不變）。
- 表格不再填滿視窗寬度，視窗較寬時右側留空——這是「貼齊」的直接結果。

## 曾考慮的替代方案

- **固定欄寬（`colgroup` + `table-layout: fixed`）**：尺寸可精確推導、與資料無關，但要多養一組欄寬常數，內容超過欄寬時還會被裁切。自然寬度既然量得到，就不需要人工指定。
- **保留 `width: 100%`，只縮小欄距**：欄位仍隨視窗拉開，能省下的寬度有限，等於沒解決問題。
- **保留水平捲動，只把下限放寬**：使用者要的是「縮到最小時所有欄位都在」，捲動不會把欄位帶回畫面。
- **只把最小尺寸改成內容尺寸，啟動時仍沿用記住的尺寸**（第一版做法）：實測啟動時視窗維持 724×480，沒有貼合內容，使用者要的「縮到貼合欄位邊界」不會發生。
- **還原記住的尺寸，但只在比內容大時才縮小**：與上一項等價，且使用者拉大過的視窗仍會蓋掉貼合結果。
- **保留尺寸持久化，只把第一次啟動改成貼合**：偏好檔已經存在時看不到效果。
- **量測時把新增表單一起算進去**：表單可換行，不會造成水平溢出，算進去只會讓尺寸被一個可自動折行的區塊決定。
- **`scrollbar-gutter: stable` 預留捲軸空間**（第二版做法）：寬度需求不隨捲軸出現而變，不必收斂，但沒有捲軸時右緣會多出一條約 17px 的空白，使用者直接看得出來。改為量測實際捲軸寬度。
- **最小高度沿用 480**：與縮放下限的基準不同（480/760 = 0.63 對 0.85），視窗形狀會隨寬度變形而變。
