# ADR-0013：`window.setSize` 收外框尺寸、`net.get` 的 `timeout` 不生效

- 狀態：已決定
- 日期：2026-10-16

## 背景

P4b / P5 驗收時發現兩個現象：

1. **每次重啟視窗都變小。** 使用者把視窗調到內容尺寸 724×433，`portfolio.json` 也記下 724×433；下次啟動 `applyWindowSize` 用同一組數字呼叫 `setSize`，結果內容尺寸變成 566×347，再下次變成 546×347，最後卡在 700×480（內容 546×347）。視窗縮到最小後表格必須水平捲動，右側欄位（今日報酬金額、今日報酬率，編輯模式下再加「操作」）看不到。
2. **啟動時偶爾抓不到現價，且 `logs/app.log` 沒有任何失敗紀錄。** 手動啟動、以相同 `portfolio.json` 重現時又正常。

## 實測

2026-10-16，本機顯示縮放 125 %（`devicePixelRatio = 1.25`），啟動後在 `main()` 末端直接呼叫 API：

| 呼叫 | 結果 |
|---|---|
| `window.setSize({ width: 724, height: 480 })` | `window.getSize()` = 724×480、`window.innerWidth × innerHeight` = 566×347 |
| `window.setSize({ width: 900, height: 700 })` | `window.getSize()` = 900×700、`window.innerWidth × innerHeight` = 706×523 |
| `getText('http://192.0.2.1:80/', 3)`（不可達位址） | 21,066 ms 才失敗（OS 的 TCP 逾時），**指定的 3 秒被忽略** |
| `getText('http://203.0.113.1:80/', 3)` | 21,045 ms 才失敗，同樣忽略 3 秒 |
| `getText(MIS, 10)` | 89 ms，200 |

換算關係：`內容尺寸（CSS px） = （外框尺寸（實體 px） − 邊框）/ devicePixelRatio`，邊框約 17.5×46.25 實體 px。

結論：`window.setSize` 的 `width` / `height` 與 `minWidth` / `minHeight` 是**外框尺寸、實體 px**，與 `window.innerWidth`（內容尺寸、CSS px）差一個 `devicePixelRatio` 加標題列與邊框；`Neutralino.net.get` 的 `timeout` 選項**不生效**。

## 決策

1. `portfolio.json` 的 `windowWidth` / `windowHeight` 繼續存**內容尺寸（CSS px）**，語意等於 `window.innerWidth` / `innerHeight`。還原時換算成外框尺寸：

   ```
   外框 = max(內容, 最小內容) × devicePixelRatio + 邊框
   ```

   邊框在啟動時以 `getSize()` 與 `innerWidth` 量測（兩者相減），`minWidth` / `minHeight` 一併換算。縮放因子（`devicePixelRatio`）與邊框都是執行期量測，不寫死。
2. `resize` 監聽要等首次套用完成才開始寫回 `portfolio.json`。框架建立視窗的初始尺寸會先觸發一次 `resize`，若那時就寫回，`applyWindowSize` 會反過來套用初始尺寸（實測出現過偏好 724×480 被 866×571 蓋掉）。`applyWindowSize` 另等到 `window.innerWidth` 反映新尺寸才回傳（最多 500 ms），否則啟動記錄會記到調整前的舊尺寸。
2. `src/services/http.ts` 的 `net` 路徑補上 JS 端逾時：以 `timeoutSeconds` 計時，逾時就讓請求失敗。curl 路徑維持由 `curl.exe -m` 負責。
3. MIS 回應缺少請求中的代號時，記 `WARN quote.missing`（列出代號），**不**計入失敗次數、**不**觸發降級。

## 理由

- 兩個現象都是框架 API 與文件不一致造成的：不換算就每次啟動縮小；不補逾時，連線卡住時畫面會靜默留白，連 `quote.fail` 都不會出現，事後無從診斷。
- 保留「內容尺寸」語意讓既有設定值不必遷移，使用者的視窗大小原樣還原。
- `timeout` 是既有程式碼本來就打算有的行為（`DEFAULT_TIMEOUT_SECONDS = 10`），補上計時器是讓實作符合原意，不是新增策略。
- 查無資料（MIS 的佔位物件）不是連線失敗，列為 WARN 可留下痕跡，又不會把已下市代號誤判成 MIS 掛掉而切到 Yahoo。

## 後果

- `applyWindowSize` 依賴 `getSize()` 在啟動時回報的邊框；若日後框架修好 `setSize` 的單位，這裡要一起改回。
- 逾時計時器不會取消底層請求，只讓呼叫端提早失敗；`keepAlive: false` 因此每次請求都是獨立連線。
- 逾時失敗會計入 `quote.fail` 與降級次數，`logs/app.log` 會出現 `請求逾時 N 秒`。
- 視窗最小尺寸現在以**內容尺寸** 700×480 為準（外框約 892×646 實體 px）。先前 `minWidth: 700` 被當成外框，實際最小內容只有 546×347。

## 曾考慮的替代方案

- **`windowWidth` / `windowHeight` 改存外框尺寸（`getSize()`）**：最簡單，但既有設定值會被當成外框解讀，第一次啟動視窗會比使用者設定的小一截；且欄位語意與 `innerWidth` 脫鉤，不易理解。
- **用 `schemaVersion` 遷移既有設定值**：遷移需要知道邊框與縮放因子，但那些值只能在執行期量測，載入階段拿不到，得先開窗再遷移，複雜度換不到好處。
- **逾時交給框架**：實測無效（見上表），維持原狀就等於沒有逾時。
- **查無資料視為抓取失敗**：會讓持有已下市代號的使用者被降級到 Yahoo，代價大於好處。
