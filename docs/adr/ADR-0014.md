# ADR-0014：非交易時段首抓失敗時延遲重試一次

- 狀態：已決定
- 日期：2026-10-16

## 背景

F5 規定「啟動後立即抓一次，若為非交易時段則抓一次即停」。驗收 P4b 時使用者回報：重新開啟 app 時現價欄與四個報酬欄都是「—」，而 `logs/app.log` 沒有任何失敗紀錄；手動重現時又正常，找不到穩定觸發條件。

排查後確認有兩條「抓不到價但不算失敗」的路徑（詳見 ADR-0013）：

- `net.get` 的逾時不生效，連線卡住時要等到 OS 逾時（實測 21 秒）才會失敗；
- MIS 對查無資料回傳佔位物件，HTTP 仍是 200，先前也沒有任何記錄。

兩者都不會讓 `attempt` 回報失敗。而 F5 在非交易時段只抓一次就停止輪詢，因此那一次沒拿到報價，畫面就整段留白到下次啟動。

## 決策

非交易時段啟動時，首抓若沒有取得全部 targets 的報價，延遲 5 秒（`STARTUP_RETRY_MS`）重試一次，之後不再重試。判定用 `codesWithoutQuote(targets, batch.quotes)`，同時涵蓋「連線失敗（`batch` 為 `null`）」與「來源回傳佔位物件」兩種情況，並記 `WARN quote.retry`。

交易時段不變：輪詢每 5 秒一次，本來就會自然重試。

## 理由

- 首抓失敗沒有下一次，是使用者症狀中唯一沒被其他修正覆蓋的成因；補一次重試就能涵蓋「第二次（連線已暖）成功」這種最常見的情況。
- 重試只有一次，不違反 F5 的「時段外完全停止輪詢」：沒有建立輪詢，只是一次延遲的單次抓取。
- 判定用「有沒有取得報價」而不是「有沒有丟例外」，才能覆蓋佔位物件這條靜默路徑。

## 後果

- 持股含永久查不到的代號時，每次啟動會多一次請求（也多一筆 `quote.missing`）。代價是一次請求，換到的是不再靜默留白。
- 重試後仍失敗就維持留白，但 log 會有 `quote.fail` / `quote.missing` / `quote.retry` 可追。
- `refreshOnce()`（新增持股後補抓）不套用這個重試，維持單次補抓。

## 曾考慮的替代方案

- **維持抓一次即停**：規格最單純，但使用者的症狀無解，只能靠 log 事後診斷。
- **固定間隔持續重試到成功**：等於在非交易時段恢復輪詢，違反 F5。
- **只在丟例外時重試**：覆蓋不到佔位物件（MIS 回 200），會漏掉使用者實際遇到的那條路徑。
