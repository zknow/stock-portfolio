# ADR-0004：儲存於 `config/` 下的單一 JSON

- 狀態：已決定
- 日期：2026-10-16

## 背景

需要決定庫存與 UI 偏好要存在哪裡，以及用什麼形式。Neutralino 提供三種途徑：

- `Neutralino.storage` 的 key-value API（資料落在 `.storage` 目錄）
- `Neutralino.filesystem` 自行讀寫檔案
- 自行接入 SQLite

位置上有兩個軸：放在應用程式目錄（`dataLocation: "app"`，預設），或放在系統使用者資料目錄（`dataLocation: "system"` + `os.getPath('data')`）。

另有一個硬性限制：**`neutralino.config.json` 必須位於專案根目錄**，Neutralino 不接受其他位置。因此 `config/` 不能作為 Neutralino 設定的容器。

## 決策

使用 `Neutralino.filesystem` 讀寫 `config/` 下的兩個 JSON 檔：

| 檔案 | 內容 |
|---|---|
| `config/portfolio.json` | 持股清單 + UI 偏好（排序鍵、排序方向、視窗寬高）+ `schemaVersion` |
| `config/symbols.json` | 代號對照表快取（含 `updatedAt` 日期） |

並採 `dataLocation: "app"`（維持預設），資料留在應用程式目錄。

## 理由

- 需求已明列 `config/` 為設定檔目錄。把庫存與偏好放進去，符合既定結構，不需額外發明目錄。
- 單一 JSON 檔可被使用者直接開啟、檢視、手動修正、複製備份、納入版控。這對一個「自己的庫存」檔案是很實際的價值。
- `storage` API 雖然程式最簡單，但資料藏在 `.storage` 目錄、以 `.neustorage` 檔案形式存在，使用者不易找到、不易備份，出問題也難修。
- SQLite 對這個資料量（數十筆）完全不划算，且需要處理原生擴充與 Windows binary。
- `dataLocation: "app"` 讓資料緊鄰程式，符合「綠色可攜」的使用方式：解壓到哪、資料就在哪。以 `dataLocation: "system"` 存放雖然在正式安裝情境下更正確，但會讓檔案變得難找，而本專案是單機個人工具，可攜性優先。
- `schemaVersion` 是為了讓 ADR-0002 提到的「日後轉型為記帳工具」有一條明確的遷移路徑。

## 後果

- `filesystem.writeFile` **不保證**自動建立父目錄，寫入前必須先呼叫 `filesystem.createDirectory`（自 v5.0.0 起支援遞迴建目錄）。
- Neutralino v6.10.0 新增 `filesystemScopes` 限制。**必須留空或省略**，否則範圍外的檔案存取會以 `NE_FS_SCOPERR` 失敗。
- 若將應用程式安裝到唯讀位置（例如 `Program Files`），寫入會失敗。本專案的因應方式是採綠色可攜：解壓後執行，目錄可寫。此限制記於本 ADR，日後若要發行安裝版必須重新檢視。
- `logs/app.log` 與 `config/` 兩個 JSON 檔必須列入 `.gitignore`（前者是執行期產物，後者是個人資料）。
- `portfolio.json` 損毀時的行為必須明確定義：拒絕覆寫、寫入 log、UI 顯示錯誤並保留原檔，不可靜默重建。

## 曾考慮的替代方案

- **`Neutralino.storage` key-value API**：程式最簡單，但資料不透明、不易備份、不易手動修。與「自己的庫存自己看得懂」的期待衝突。
- **系統 AppData（`dataLocation: "system"`）**：正式安裝情境最正確，但使用者難以找到檔案、難以備份，對單機工具是過度設計。
- **另建 `data/` 目錄**：職責劃分最清楚（執行期資料 vs 設定），但打破了需求已定的目錄清單。
- **每個持股一個檔案**：檔案數量隨持股成長，讀寫與排序都變複雜。
- **SQLite**：正規但對這個資料量不划算，且引入原生相依。
