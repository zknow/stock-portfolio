# ADR-0005：TypeScript + Vite，不引入框架

- 狀態：已決定
- 日期：2026-10-16

## 背景

Neutralinojs 只提供原生 API（視窗、檔案、網路），前端技術完全自由。可選項包括：

- **(a)** Vanilla JS + HTML/CSS，無建置步驟
- **(b)** TypeScript + Vite，不引入 UI 框架（原生 DOM）
- **(c)** React / Vue + Vite

另外，實測發現 **Neutralino 沒有官方的 Vite 模板**（`neutralinojs/neutralinojs-vite-template` 回 404），官方只有 `neutralinojs-minimal` 與 `neutralinojs-zero`。因此 (b) 需要自行接入 Vite。

## 決策

**(b) TypeScript + Vite，不引入 UI 框架。** 由 `neutralinojs-zero` 骨架起步，手動接入 Vite 與 TypeScript 工具鏈。

## 理由

- **TypeScript 的價值集中在報價解析**。本專案要處理外部 API 的不可信輸入：MIS 的佔位物件（`c === ""`）、當日無成交（`z === "-"`）、`trade.z` 與 `z` 的雙軌、Yahoo 與 MIS 兩套完全不同的欄位名。這些都是型別能立即抓到的錯誤，也是這個專案唯一真正複雜的地方。
- **不需要框架**。整個 UI 是一個表格（9 欄）、兩個 modal（新增/編輯）、一顆模式切換鈕、一條狀態列。沒有複雜的狀態樹、沒有跨元件共享狀態、沒有路由。引入 React 只會帶來依賴樹、建置時間與心智負擔。
- **Vite 帶來的好處與框架無關**：HMR 讓 UI 調整立即生效，dev server 與 `neu run` 可透過 `cli.frontendLibrary` 直接串接。
- 排除 (a) 的理由是沒有型別檢查，而報價解析正是最容易出錯的部分。
- 排除社群 Vite 模板的理由是它們多半綁定 React（如 `Cloudwerk/neutralinojs-vite-react-ts`），或維護狀態不明。自行接入 Vite 的設定量很小（`documentRoot`、`cli.frontendLibrary` 六個 key），換來完全可控。

## 後果

- 需要自行維護 `vite.config.ts`、`tsconfig.json` 與 `neutralino.config.json` 的串接：

```json
"documentRoot": "/dist/",
"cli": {
  "binaryVersion": "6.10.0",
  "resourcesPath": "/dist/",
  "frontendLibrary": {
    "patchFile": "/index.html",
    "devUrl": "http://localhost:5173",
    "projectPath": "/",
    "initCommand": "npm install",
    "devCommand": "npm run dev",
    "buildCommand": "npm run build"
  }
}
```

- 沒有框架意味著 DOM 操作要自己寫。這在本專案的規模下是可接受的，因為表格重繪是唯一的動態行為。若表格重繪變成瓶頸，優先是改成局部更新，而非引入框架。
- `AGENTS.md` 將「不引入 UI 框架」列為硬性約束：新增任何 npm 依賴（含 devDependency）都需要一篇 ADR。這條約束的目的是防止依賴樹無聲膨脹。
- 型別定義（`src/domain/types.ts`）成為跨層契約，`Quote` 型別是 domain 與 services 之間唯一的介面。

## 曾考慮的替代方案

- **Vanilla JS 無建置步驟**：最陽春、改檔即生效、零依賴，但沒有型別檢查，報價解析與兩套 provider 的正規化容易出錯，且無法寫 vitest 測試。
- **React + Vite**：生態最大、UI 狀態好管，但對此規模是過重依賴，且會讓「新增依賴需 ADR」的約束失去意義。
- **Vue + Vite**：比 React 輕、模板直覺，但仍是框架依賴，理由同上。
- **使用社群準備好的 Vite 模板**：省下接入設定，但模板綁框架或維護狀態不明，風險大於省下的工作量。
