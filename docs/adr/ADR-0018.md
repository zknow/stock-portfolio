# ADR-0018：使用者縮放自行實作，擋掉 WebView2 的原生頁面縮放

- 狀態：已決定
- 日期：2026-10-19

## 背景

F11 的縮放一直是「由視窗寬度推得」：`scaleFactor(width) = max(width / 1100, 0.85)`，視窗尺寸再從內容的自然寬度推得（ADR-0016）。使用者想把介面看得更大，只能把視窗拉寬，而且寬度要超過 935 之後字級才跟著放大。

使用者實際的操作是 Ctrl+= / Ctrl+- 與 Ctrl+滑鼠滾輪，走的是 WebView2 的原生頁面縮放，並要求介面要跟著等比放大、倍率要記住並在下次啟動還原。實測原生縮放的行為：

- Ctrl+= 三次（175%）後視窗剛好跟著長到 782×568。
- 再 Ctrl+滾輪三次（200% 以上）視窗不再變動，**現價與兩個報酬欄整欄被裁掉**，表格還出現垂直捲軸。

原因是原生縮放放大的是 CSS px 而不是版面：`--scale` 與視窗尺寸都不知道它發生過，只有 `devicePixelRatio` 會變。而 `@neutralinojs/lib` 沒有任何 zoom API（`Neutralino.window` 既沒有 getZoom 也沒有 setZoom），**讀不到也設不回去**，所以「記住倍率、下次還原」不可能靠它完成。

## 決策

1. **自行實作縮放**：`Ctrl+=` / `Ctrl++` 放大、`Ctrl+-` 縮小、`Ctrl+0` 回 100%、`Ctrl+滾輪` 每格一跳；倍率 80%–200%、級距 10%，夾限與套用在 `ui/scale.ts`，事件對映在 `ui/zoom.ts`。
2. **一律擋掉原生縮放**：`keydown` 與 `wheel`（`{ passive: false }`）在 `ctrlKey` 成立且鍵是上述組合時 `preventDefault()`；滾輪即使已達上下限也照樣擋，不讓原生縮放接手。其他 Ctrl 組合鍵不受影響。
3. **倍率乘在既有因子之上**：`scaleFactor(width, zoom) = max(width / 1100, 0.85) × zoom`。ADR-0011 / 0016 / 0017 的規則不變，使用者倍率只是最外層的一個乘數。
4. **量測固定在「下限 × 倍率」**：`measureMinSize()` 量的是 `MIN_SCALE × zoom` 下的內容自然寬度，因此放大後視窗跟著長大，貼合關係與原本一致。
5. **倍率持久化**：`portfolio.json` 加 `zoom`（預設 1），與 `sortKey`、`sortDirection`、`returnDisplay` 同一組 UI 偏好（F14）。`schemaVersion` 維持 1，缺欄位或非有限數值回預設；超出上下限的值由 `setZoom` 夾限，下次寫檔就收斂回範圍內。
6. **畫面不顯示目前倍率**：沒有指示器，倍率只影響畫面大小。

## 理由

- 原生縮放不可能滿足「記住並還原」：既沒有讀取目前縮放的 API，也沒有設定它的 API。
- 原生縮放與貼合尺寸是兩套互不相干的機制：貼合尺寸是「內容自然寬度（CSS px）＋外框」，換算時用 `devicePixelRatio`；原生縮放只改 `devicePixelRatio`，而重算尺寸需要 `minSize` 剛好變動才會被觸發。175% 時量到的內容寬度有小數變動而僥倖重算成功，200% 沒有觸發就破功。
- 走 CSS 變數的既有縮放機制（ADR-0006）本來就是「整個 UI 一起放大縮小」的實作，加一個乘數比另外引進一套縮放疊在它上面簡單，量測與貼合也不必改寫。
- 每格 10% 是線性級距：值只會落在 0.8、0.9 … 2.0 這 13 個格點，`Ctrl+0` 回到的 100% 與預設值是同一個數，寫進偏好檔的數字也固定。

## 後果

- 實測（2 檔持股；外框寬 16 CSS px，因此視窗寬 = 內容自然寬 437 × 倍率 + 16）：
  - 100% 453×341、110% 497×371、130% 584×431、150% 672×492、180% 803×583、200% 890×643（實體 px）。
  - 80%（下限）366×281 到 200%（上限）890×643 之間任一級距，7 欄、總計列、狀態列都完整可見，沒有裁切也沒有水平捲軸。
  - 200% 時視窗寬 874 CSS px 仍小於 935，寬度項取到的還是下限 0.85，所以套用的縮放等於量測用的縮放，貼合完全自洽。
- 倍率寫入 `portfolio.json`：重啟直接開在該倍率（實測 `zoom: 1.5` → 672×492）。
- 視窗寬度超過 935 時寬度項與倍率同時作用（`max(width / 1100, 0.85) × zoom`）。此時寬度項會讓實際內容比量測值大，實務上要「內容自然寬度大於約 600 CSS px 且倍率接近 200%」才會遇到。
- 用滑鼠改變視窗大小不會改動倍率；倍率只有 Ctrl 組合鍵與 Ctrl+滾輪會動。
- `ui/zoom.ts` 的按鍵與滾輪對映是純函式，可用 vitest 覆蓋；只有事件綁定需要 DOM。

## 曾考慮的替代方案

- **沿用原生縮放，只讓視窗跟著長大**：要辨識縮放變化（只有 `devicePixelRatio` 會變）再重算尺寸，而且「下次啟動還原倍率」仍然做不到。
- **`transform: scale` 縮放整個 `.app`**：字級與間距確實等比，但與 ADR-0016 的兩趟量測打架（`getBoundingClientRect` 回的是 transform 後的尺寸），也可能出現非整數像素的模糊邊緣。
- **從框架設定關閉瀏覽器快捷鍵**（WebView2 的 `AreBrowserAcceleratorKeysEnabled`）：`neutralino.config.json` 沒有這個選項，而且關掉它會一併關掉其他快捷鍵。
- **等比級距（1.1 倍連乘）**：更接近瀏覽器體感，但值會變成 0.8、0.88、0.97…，要另外定義格點與「100%」的回到點。
- **把倍率寫進另一個檔案**：偏好只有一組，多一個檔案就多一個要同步的來源（與 ADR-0004、ADR-0008 同一個考量）。
