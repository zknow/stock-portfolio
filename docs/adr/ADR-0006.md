# ADR-0006：縮放改用內容等比，不鎖定視窗寬高比

- 狀態：已決定
- 日期：2026-10-16

## 背景

需求為「可以等比縮放 APP 大小（四角斜向拖拉）」。初期的解讀是**鎖定視窗寬高比**：拖拉任一角落時視窗按固定比例縮放，UI 全部一起放大縮小、不留白。

實測 Neutralino v6.10.0 後發現三個事實推翻了這個做法：

1. **不支援固定寬高比。** `modes.window.*` 只提供 `width`、`height`、`minWidth`、`minHeight`、`maxWidth`、`maxHeight`、`resizable`，沒有 aspect ratio 相關設定，`window.setSize` 也沒有。
2. **沒有 `windowResize` 事件。** `Neutralino.events.on` 的事件清單中沒有視窗縮放事件，只有 `windowClose`、`windowFocus`、`windowBlur`、`windowMinimize`、`windowRestore`、`windowMaximize`、`windowFullScreenEnter/Exit`。
3. **沒有 `window.setPosition`**，需改用 `window.move(x, y)`。

因此「鎖定寬高比」只能靠監聽 resize 後自行呼叫 `window.setSize` 修正尺寸，這會在使用者拖拉的當下與作業系統的視窗管理器互搶控制權。

## 決策

**放棄鎖定寬高比。視窗自由拖拉，內容依視窗寬度對基準寬 1100 等比縮放。**

- 縮放因子 = 視窗寬度 / 1100
- 套用到字級、間距、欄寬，驅動方式為更新 CSS 自訂屬性
- 監聽對象為 DOM `window` 的 `resize` 事件
- 視窗最小尺寸由 `modes.window.minWidth / minHeight` 限制（700 × 480）

## 理由

- 使用者要的視覺效果是「整個 UI 一起放大縮小」，這一點由內容等比縮放完整達成，且不受視窗寬高比影響。
- 自行實作 aspect lock 需要在每個 resize 事件重新計算並回呼 `setSize`，而 `setSize` 本身又會觸發下一次 resize，形成回饋迴圈。實際體感是拖拉時畫面抖動或閃爍，比「比例沒有鎖住」更糟。
- 用 CSS 變數驅動縮放是純樣式行為，沒有額外的 API 呼叫、沒有競態、沒有抖動，且可在瀏覽器 devtools 中直接調整驗證。
- 以寬度而非較小邊作為縮放基準，是因為表格是寬向排列的 9 欄，寬度才是版面壓力的來源。窄而高的視窗不會讓欄位擠壞。

## 後果

- 視窗被拉成極端寬高比時，內容會依寬度縮放，垂直方向可能出現留白或需要滾動。這是刻意的取捨：穩定優先於完美比例。
- `scale.ts` 的職責僅為「監聽 resize、算出因子、寫入 CSS 變數」，不涉及 Neutralino API。
- 縮放因子必須有上下界，避免視窗拉極小時字級縮到不可讀。下界由 `minWidth: 700` 對應到約 0.64 倍自然守住。
- 必須在 DOM `resize` 上做節流，避免拖拉期間每一像素都重算。
- 此決策記錄了「Neutralino 沒有原生 aspect lock 與 resize 事件」這個事實，避免日後被重新提議。

## 曾考慮的替代方案

- **硬鎖寬高比（自訂 hack）**：在 resize 事件中回呼 `setSize` 修正尺寸。視覺上最接近原生等比縮放，但與使用者拖拉互搶控制權，可能抖動、閃爍甚至進入回饋迴圈。
- **僅做 RWD，不縮字**：靠 flex/grid 自適應排版，字級固定。最簡單、最省 I/O，但不符合「等比縮放」的需求語意。
- **以 `transform: scale` 縮放整張畫布**：字級間距完全等比，但視窗比例與畫布比例不符時會留白，且 devtools 除錯與 hit-testing 較麻煩。
- **以較小邊為縮放基準**：在窄高視窗下字級不會過大，但表格的主要壓力來自寬度，基準選錯會讓常見情境不理想。
