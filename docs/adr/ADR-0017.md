# ADR-0017：欄寬下限貼齊內容，比內容寬時欄位一起拉寬填滿邊界

- 狀態：已決定
- 日期：2026-10-18

## 背景

ADR-0016 決定 `table { width: max-content }`：欄寬完全由資料決定，不隨視窗拉開，好處是「內容需要多寬」可以實測，並由它推出視窗的最小尺寸。代價寫在 ADR-0016 的後果裡：**表格不填滿視窗寬度，視窗拉寬時右側留空**。

使用者要求：手動把介面拉寬時，欄位（含欄頭）應該同步跟著拉寬、貼到邊界，而不是固定住。

## 決策

1. `table` 保留 `width: max-content`，加上 `min-width: 100%`。表格寬度 = max(內容自然寬度, 容器可見寬度)：視窗不比內容寬時完全等於內容自然寬度（ADR-0016 的行為不變），比內容寬時填滿，多出來的寬度由瀏覽器的 auto table layout 分配給各欄。
2. **視窗尺寸的推導完全不變**（ADR-0016 的決策 2–7 全部維持）：量測時 `.app` 設 `width: max-content`，此時 `min-width: 100%` 的百分比對到尺寸未定的容器，依規範視為 0，量到的仍純粹是內容自然寬度，不會因為這個改動而回饋放大。
3. 取代 **ADR-0016 決策 1 的後半段**（「表格寬度由資料決定，不隨視窗拉開」）與其後果中「表格不再填滿視窗寬度，視窗較寬時右側留空」那一條。ADR-0016 其餘決策（尺寸由內容推得、尺寸不持久化、捲軸寬度即時量測、套用後收斂、新增表單排除）不受影響。前述 ADR 本文依專案規則不修改。

## 理由

- 使用者要的兩件事本來就是同一個表格寬度的下限與上限：縮到最小時所有欄位都在（下限＝內容自然寬度），拉寬時不要留白（上限＝容器寬度）。`min-width` 正好就是「下限」這個語意。
- 用 `min-width: 100%` 而不是把 `width` 改成 `100%`：`width: 100%` 會讓表格寬度由容器決定，量測階段（容器尺寸未定）就量不到內容寬度，ADR-0016 的整個尺寸推導會失效。`width: max-content` + `min-width: 100%` 在量測階段退化為純內容寬度，兩件事互不干擾。
- 多出來的寬度交給瀏覽器的 auto table layout，不自己定分配規則（等分、按內容比例、只補最後一欄都得另外維護常數）；欄頭與數值的對齊規則（F1）與欄寬無關，不受影響。

## 後果

- 實測（1 檔持股、縮放固定在 0.85，即視窗寬 ≤ 935，所以以下兩個尺寸的字級相同，差異純粹來自拉寬）：
  - 視窗 421×290（貼合內容）：欄頭 x 為 23 / 91 / 166 / 217 / 332 / 383 / 459。
  - 視窗 900×400：欄頭 x 為 23 / 166 / 381 / 517 / 730 / 866 / 1042，最右欄右緣 1103 + 儲存格 padding 13 = **1116 = 視窗內容右緣**（完全貼齊）。
- 拉寬時欄與欄之間會出現較大的空白（欄內內容仍靠左／靠右對齊不動），這是填滿邊界的直接結果。
- 有垂直捲軸時，`100%` 指的是捲軸左側的可見寬度，所以不會出現水平捲軸：實測 12 檔持股（視窗 481×331、垂直捲軸 14.4 CSS px）最右欄右緣貼齊捲軸左緣，畫面沒有水平捲軸。
- 縮放行為不變：視窗寬 935 以上字級仍隨寬度放大（ADR-0011 的 0.85 夾限不變），此時「填滿」與「放大」同時發生。
- 貼合最小寬度不變：1 檔持股仍是 421×290、12 檔持股仍是 481×331，與改動前相同（量測不受 `min-width` 影響）。

## 曾考慮的替代方案

- **`table { width: 100% }`**：欄位一樣會填滿，但視窗最小尺寸的量測會跟著容器跑，量不到內容自然寬度。
- **維持 `width: max-content`，只把最後一欄撐開**：多出來的寬度全給最右欄，其他欄頭不會「同步拉寬」，不符合要求。
- **自己指定分配比例（例如按內容寬度加權）**：需要多養一組與資料相關的規則，而瀏覽器的 auto layout 已經在分配，沒有換來可預期的好處。
- **在視窗比內容寬時改回 `width: 100%`**（用 JS 切換）：等於用腳本重做瀏覽器本來就會做的事，還要處理切換時的重排。
